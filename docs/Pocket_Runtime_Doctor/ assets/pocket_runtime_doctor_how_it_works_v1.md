# Purpose

This document defines the complete engineering workflow of Pocket Runtime Doctor.

It explains how the product transforms a software system into an observable patient, analyzes its engineering health, generates verified findings, and produces actionable reports while following the Occult Grammar Protocol (OGP).

# Objective

Pocket Runtime Doctor provides an observation-first engineering workflow.

Rather than modifying software immediately, the system first collects evidence, verifies engineering conditions, and documents findings before recommending action.

## 2. Runtime Workflow

The engineering workflow follows these stages:

Admit or Load Patient

↓

Observe

↓

Taste Engine Analysis

↓

Verify

↓

Generate Report

↓

Export Findings

↓

Discharge Patient

Each stage produces observable engineering artifacts.

# Taste Engine

The Taste Engine evaluates engineering quality without modifying the target.

Current analysis includes:

• Structure

• Runtime Health

• Risk

• Maintainability

• Overall Engineering Score

The resulting verdict determines the patient's engineering condition.

# State Management

Pocket Runtime Doctor maintains explicit runtime state.

Primary state resources include:

• doctor_patient_bridge.json

• doctor_state.json

• Local Database

• Export Reports

State is never hidden.

All engineering actions are observable.

# Engineering Principles

Pocket Runtime Doctor follows the Occult Grammar Protocol.

Principles include:

• Observe before modification.

• Verify before execution.

• State is explicit.

• Presentation remains separate from logic.

• Stable systems are preserved.

• Expand only after verification.
